# brg-02 (site) — Admin sign-in with admin and editor roles

> **GitHub Issues:** `BRG-13` (local `brg-02`) · **Phase:** P3 · **Covers:** RF-08, RNF-05
> **Counterpart:** — (does not cross layers)
> **Status:** `[x]` draft · `[x]` approved (agent, mode C, 2026-10-19) · `[ ]` implemented

Turns the issue's acceptance criteria (guests go to the login, editors get 403 on Settings and Users, admins open everything, login attempts are rate limited) into the panel access rule, the first two policies, a Users resource and the permission matrix every later P3 story applies.

## 1. Scope in this layer

**In:**

- `User` implements Filament's `FilamentUser`. Without it, Filament denies every user outside the `local` environment, so staging and production would lock everyone out.
- The panel runs in **strict authorization** mode: a resource whose model has no policy throws instead of silently allowing everything. Every later resource story ships its policy.
- The permission matrix, recorded as ADR D8.1 in this PR (closes point 8.1).
- `UserPolicy` and `SettingsPolicy` (the two admin-only models).
- A Users resource, admin only: list, create, edit and delete users and set their role.
- `app:promote-admin {email}`: turns an existing user into an admin, so the owner gets the first admin on a server (created with `php artisan make:filament-user`, which gives the default `editor` role).
- Demo data (outside production only): the seeded `test@example.com` becomes an admin, and a new `editor@example.com` is an editor, so both roles can be tried locally.

**Out / deferred (with reason):**

- Content policies (Service, Language, Faq, Post, Client, Testimonial, Page) → each resource story (HU-03–HU-08) ships its own, following ADR D8.1.
- The Settings screen → HU-09. This story ships only its policy.
- `LeadPolicy` → HU-27 (P5, vetoed in `CLAUDE.md` §5). The matrix already records it.
- Password reset by email → P5 (needs the mailer), as the issue says.

## 3. Technical contract

### 3.1 Permission matrix (ADR 8.1)

The matrix lives in ADR **D8.1** (moved there by this story, which closes point 8.1). This story ships its Settings and User rows; each later story applies its own row.

### 3.2 Panel access

- `User::canAccessPanel(Panel $panel): bool` returns true for both roles: every user in the table is Bridge staff created by an admin (there is no self-registration).
- `User::isAdmin(): bool` (`role === UserRole::Admin`) is the only role check the policies use.
- `AdminPanelProvider` adds `->strictAuthorization()`.
- Login: Filament's own (D4.5). Its built-in limit (5 attempts per minute per IP) covers the rate-limit AC; the test keeps it from being lost by a later custom login page.

### 3.3 Policies

- `app/Policies/UserPolicy.php`: `viewAny`, `view`, `create`, `update` → `isAdmin()`. `delete` → `isAdmin()` and not the same user. No `deleteAny` (no bulk delete in the table).
- `app/Policies/SettingsPolicy.php`: `viewAny`, `view`, `update` → `isAdmin()`. No `create` or `delete` methods; under strict mode Filament never offers those actions.
- Discovered by Laravel's naming convention (no registration).

### 3.4 Users resource

- Generated by `make:filament-resource User` (Filament 5 layout: resource, `Pages/`, `Schemas/`, `Tables/`).
- Form: `name` (required), `email` (required, email, unique ignoring the current record), `password` (required on create; on edit, blank keeps the current one), `role` (required, the `UserRole` options).
- `role` is not fillable (brg-35 §3.5), so the create and edit pages write it explicitly (`forceFill`) after Filament's fill. Only an admin reaches those pages (§3.3), so the protection holds everywhere else.
- Table: name, email, role, created_at. Edit and delete row actions; no bulk actions.
- Labels in Spanish through `__()` in `lang/es/admin.php` (D3.6). `UserRole` implements Filament's `HasLabel`: "Administrador", "Editor".

### 3.5 `app:promote-admin {email}`

- Sets `role = admin` on the user with that email and prints a confirmation.
- Unknown email: prints an error, exits with failure and changes nothing.
- No demotion command: an admin demotes users from the Users resource.

## 5. Implementation notes

- In tests, switch the environment with `app()->detectEnvironment(fn () => 'production')` (brg-37) and check that the panel middleware reads `config('app.env')`. If it does, set that too.
- Writing the role: the factory gets an `admin()` state that uses `forceFill`-equivalent `state(['role' => UserRole::Admin])` (factories bypass `$fillable`).
- The C3 mutation for test 12 edits `vendor/filament/filament/src/Auth/Pages/Login.php` on a backup copy and restores it; vendor is never committed.
- Larastan with `--memory-limit=1G`.
